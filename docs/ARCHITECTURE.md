# Architecture and compatibility

laci is a Linux desktop application with three layers. `laci-core` reads projects and agent stores and implements filesystem changes. The `laci` binary exposes that engine through Tauri IPC, CLI subcommands and stdio MCP. React owns the interface and talks to typed IPC requests; terminal output uses Tauri channels. The interface has two designs, Simple and Detailed, built on the same store, selectors and actions (`ui/src/simple/` and `ui/src/views/`); both send the same requests, so the engine and its contracts don't depend on the design.

## Snapshot and updates

The scanner discovers project/group folders, enriches projects with git, README, stack, tasks, metadata and history, then creates cleanup proposals and archive plans. Connector readers cache parsed history using file metadata. The snapshot cache is separate from the v1 cache and includes the home/config fingerprint so an isolated demo cannot reuse a real-home scan.

The desktop returns its latest snapshot while one worker handles queued refreshes. Filesystem events are batched for 900 ms. Refresh scopes merge: a full scan subsumes agent, report and project refreshes. Reads and watch-directory enumeration run outside the engine mutex. A result is installed only if its captured mutation revision is still current; continuous watcher events request one follow-up without rejecting each useful result.

Agent-store updates reread and relink history, retaining git, README, tasks and size when discovery finds the same project graph. A graph change promotes that work to a full scan, reusing the history already loaded. Project events refresh the owning project; task and metadata edits reread their markdown. Nonrecursive filesystem watches are bounded and enumerated again when directory topology, configuration or open listings change. Activity changes notify the Log. Dependency and build directories are excluded.

Session reports come from the folder chosen in Settings (`reportsDir`). Every scan and agent pass attaches them after history is linked, because a report reaches projects through the sessions it names. A change in that folder requests a reports-only refresh: the folder is listed again, changed files are parsed again (facts cached by size, mtime, ctime and inode in `reports-v3.json`, which keeps up to 40 open items per report) and every report is linked again, without a project or agent pass. The folder is watched even past the watch budget. A report links to the deepest project containing a path in its header, the folder its session started in, or the latest cwd of a session it names, so a project Laci moved keeps its reports. The snapshot carries the newest 1,000 with their plain-text summary and up to eight open items; the text is read on request. A report linked to several projects also carries `byProject`, each project's own open items: those that name it (its folder name, as a word or the end of a path), else, for an item that names none, the one linked project its sessions worked in, else none. Home, Today and `open_items` for one project read these. Open items the user closed are kept in Laci's data folder, keyed by report file name and a hash of the item's text. They are left out of a report's open items and counts, so an item stays closed while its text is unchanged and opens again when the report rewords it.

PTY sessions belong to the Rust process. Each tab has its shell, input writer, resize handle, exit status and bounded output replay. Reattaching after a window reload replays recent output. Closing a tab or exiting the app terminates its shell.

## Shared disk contracts

| Location | Contract |
| --- | --- |
| `~/.config/laci/config.json` | Existing roots, presets, custom connectors, apps and theme; optional archiveDir, reportsDir, backupDir, backupOnly (the projects the copy of AI chats takes), design (`simple` or `detailed`) and updates (`daily` or `off`). `rootIdentities` records the device and inode of the roots, archiveDir and backupDir. Settings that exist but can't be read are never written over |
| The `reportsDir` folder | Read only: plain `*.md` files directly in it, except `README.md` and dotfiles |
| `<project>/.laci.md` | Existing frontmatter and Summary/Next/Notes sections |
| `~/.local/share/laci/journal/` | v1 move/rewrite/metadata steps and completion state |
| `~/.local/share/laci/backup/` | Original rewritten bytes and timestamps for undo |
| `~/.local/share/laci/activity.jsonl` | Existing Log entries, supersession keys and undo records |
| `~/.local/share/laci/report-items.json` | Report items closed in Laci: report file name → item key → state (done, dropped, moved), time, actor, note and text |
| `~/.local/share/laci/mcp-backups/` | Copy of an agent's settings file, taken before Laci changes its MCP setup |
| `~/.local/share/laci/history/`, or the `backupDir` folder | The copy of AI chats, of every project or of those `backupOnly` names: `<connector>/<path in the agent's store>.zst`, one zstd frame per file, and a `.laci-copy` marker at the top. Nothing in it is ever removed but temporary files of a stopped run and plain files from before 3.1 once their packed copy is checked |
| `~/.local/share/laci/backup.json` | When the copy of AI chats last ran and what it holds |
| `~/.local/share/laci/lock` | Cross-process PID lock compatible with v1 |
| `~/.cache/laci/` | Disposable parser/snapshot caches, including `reports-v3.json`, and `updates.json` (when Laci last looked for a new version); v2 cache names are separate |

The environment honors `XDG_CONFIG_HOME` and `XDG_CACHE_HOME`. Data retains the v1 location under the home folder. `LACI_HOME` redirects all locations to an isolated home and ignores the caller's XDG overrides.

## Filesystem changes

Project paths are authorized under home and explicitly selected scan/archive folders. Settings canonicalize selected external directories; replacing a selected root or a child with an escaping symlink is refused. Internal connector stores retain their home boundary. The reports folder is selected and canonicalized the same way but grants no project access; home, its ancestors and Laci's own folders are refused. Each read checks again that neither the folder nor its path became a link, opens the file without following a link, and accepts only a report listed in the snapshot. Fixed parser/config/scanner regexes initialize once.

Move/archive/Tidy actions validate paths and active processes, acquire a cross-process lock, persist a journal, then execute the steps. Destination collisions and linked write paths are refused. Cross-filesystem copies preserve content and timestamps before removing their source. A failed step rolls completed steps back. Undo restores rewrites before moving folders to their original paths, while refusing collisions with newer data.

Archive preview and execution share the same destination planner. Configured archive folders are scanned automatically. A custom destination outside the current scan roots adds only that project path to config, with the config bytes journaled for Undo. A later settings edit prevents that Undo from overwriting the new config. A move journal can restore a missing selected project root only under its original parent device and inode; ordinary browsing cannot use that exception. Mounted roots themselves are refused as move sources. An external XDG config override authorizes only its exact config.json for journal backup/restoration, without granting project access to adjacent files.

Every selected root containing an archive destination, including a nested or standalone archive folder, is checked against its saved device/inode at preview and again under the mutation lock. Ordinary Settings saves preserve that identity; clearing, saving and reselecting explicitly accepts a replacement. Legacy selections without identity remain compatible.

Project removal uses a separate Trash action and preserves external agent history. A live remote ref check is performed only when previewing/removing a selected project, never in background scans. Clean worktree, index flags, refs, stash, worktree topology and process guards are checked again after the remote answers. Only exact advertised branch/tag tips authorize removal, with conservative refusal for unmatched local branches, tags and other non-remote refs. Local backups must use independent object storage. Trash recovery belongs to the system file manager, so the activity entry does not advertise journal Undo. Moves and archives also refuse paths that would relocate Laci's config, cache or recovery data.

Archive Undo restores the saved whole `.laci.md`, so edits made to that file while archived can be replaced. Dependency cleanup deletes those folders for good, since the Trash would keep the space taken; the next install or build brings them back, and journal Undo does not.

Metadata, task, notes and settings changes also share the lock and activity log. Task paths must belong to the selected project. Checkbox changes retain the displayed file, text and occurrence so unrelated line shifts do not target a duplicate. A changed duplicate count or ambiguous legacy record is refused. New task-delete records store the removed bytes, their original position and a fingerprint of the file after deletion. Undo restores them only while that file is unchanged. Activity keys prevent undoing an older edit over a later one. `.laci.md` is excluded through git's local `info/exclude`, preserving repository ignore files.

## Desktop and MCP boundaries

Core mutation execution returns the committed result and its refresh scope. Desktop acknowledgments include a revision and a history-pending flag, and return before expensive refresh work. History-changing actions clear old Tidy proposals and gate further history mutations until a suitable refresh succeeds: one shared history file can affect several projects. Cached startup data has the same guard until the initial scan succeeds, since a crash can leave the cache behind a committed change. Safe metadata edits and navigation remain usable. Scan errors after a commit are warnings, preserving the action's success and Undo. The UI orders busy notices separately from displayed data, so continuous scans do not starve useful snapshots. Mutation notices still fence stale proposals immediately. The UI applies snapshots in revision order, guards duplicate submissions synchronously, and closes dialogs only when their initiating dialog still owns the completion.

The desktop creates one local window and uses Tauri IPC with a local-content policy. Markdown is sanitized. Local images are scoped to scanned project directories and the reports folder. Report reads, searches and opens run outside the engine lock. Commands selected by the interface are allowlisted; script/session arguments must exist in the snapshot and are shell quoted.

The window opens in the design saved in config.json. Without one, a setup made before 3.0 (its config.json has a `roots` list) opens in Detailed and offers Simple until a design is saved; a fresh install opens in Simple. The start-up script marks the page with the design and theme before it paints.

Only Rust talks to the update server (`src-tauri/src/app/update.rs`); the window has no updater permission and asks through `update/status`, `update/check`, `update/install` and `update/restart`. With `updates: "daily"` a thread asks for `latest.json` from the latest GitHub release at most once a day, starting 20 seconds after launch; `off` or no choice means it never looks by itself. A check finds a version only; downloading and installing need a click, and the download must carry the updater key's signature. Only a copy that runs from its AppImage installs; a deb, an rpm or a copy put in place by `install-desktop.sh` gets a link to the release page. The restart that finishes an update refuses while a change runs, and once it begins no change may start. `LACI_UPDATE_ENDPOINT` replaces the feed with another https address, for release candidates.

`laci mcp` serves the 14 compatible v1 tool names plus `delete_project`, the read-only `list_reports` and `open_items`, the to-do edits `edit_task`, `delete_task` and `move_task`, and `close_report_item`, over stdio without starting GTK or a window. It also offers two prompts, `review` and `work_on`; the desktop gets the same text from `assistant/prompt` for its *Review with an agent* and *Work on it* buttons. Lists and answers to changes carry compact projects (status, meta, checks, to-dos) and never the snapshot a change returns to the desktop. The list tools answer a page at a time (`limit`, `offset`, `total`, `more`) and are shaped in `mcp.rs` after the core call, so the desktop's view of the same data, such as the Log with its undo data, is unchanged. Read calls reuse a recent snapshot. Move/archive/Trash/Tidy/create/undo calls return a preview until `confirm: true` is supplied. Arguments a tool does not list are rejected. Confirmed destructive operations refresh the scan and use the same engine as the desktop.

## Providers and MCP setup

`providers.rs` holds one description per agent Laci can start: its program, argument templates, models, effort levels and MCP settings. The built-ins are Claude Code, Codex and Antigravity. The user's own tools from `config.json` are read beside them.

`mcp_setup.rs` tells whether an agent knows Laci's MCP server, and adds or removes it. Reading is passive. A change runs the agent's own command, or edits its JSON settings file after copying that file to the backup folder.

## Session launch and creation

Sessions normalize provider, UUID, title provenance, cwd, parent, source kind, update time and resume capability separately from the store/file identity. Codex metadata uses session/turn cwd, not tool-call paths. Title-index changes invalidate the title cache. Antigravity's shared last-conversation index is read-only and excluded from relocation and cleanup plans.

Session logs are read in one pass from start to end, and the pass is resumable: its state (offset, inode, a hash of the 256 bytes before the offset, the head-window counters, changed files) is cached with the facts. A log that only grew is read from the offset; a rewritten or replaced one is read again from the start. A half-written last line is left for the next pass. Ownership is still decided by the head window alone, 8 MiB and 20,000 records: lines past it update display and resume metadata only, and a log longer than the window never proves cleanup ownership. Latest cwd is separate from the complete owning-cwd set. Parse/read/traversal failures mark ownership incomplete, including Claude folder aggregates. The same pass collects what a session was about (prompts, files changed, first and last prompt, last reply, model, time spent, pull requests, the session a resume stub continued in); `READER` in `agents.rs` and the cache file name are advanced when those facts change.

While an agent is working its log changes every second; the desktop reads agent history at most every 15 seconds for such changes (`AGENT_SETTLE`). A new or removed log is read at once.

The copy of AI chats (`backup.rs`) keeps each `.jsonl`, `.json` and `.md` of the store of every connected agent that keeps one (Claude Code, Codex, Antigravity and the user's own) as one zstd frame (level 3, checksum, the length recorded in the frame header, no long-distance mode), written through a `.laci-copy-` temporary file beside it. A file is copied again only when its source's length differs from the length the frame header records; a source that shrank while it was read keeps its last copy. Each run, under the change lock, first removes temporary files of stopped runs (`.laci-copy-*` and the old writer's `.tmp??????`) and packs plain files left from before 3.1, checking every byte before the plain file goes (a plain file whose packed copy already records at least its length is the older one and just goes), and a run that packed any tells the Log how many and their size before and after (`packedCopy`); both walk only `<copy>/<connector id>` for the connectors Laci knows. Folders a move set aside or copied into (`.laci-move-*`) are never removed this way: one can hold the only copy of a chat. Backup-only sessions are read from `.jsonl.zst` (or a still-plain `.jsonl`) through a decompressing reader that shares the line loop of a session log's reader; it reads from the start with a first read's limits, cached on the packed file's stamp. One resolver, `backup::dir`, says where the copy is: `<data dir>/history`, or `backupDir`, which must exist, be reached without a link, match the identity recorded for it (a missing record is refused), hold the `.laci-copy` marker and pass `validate_backup_dir`'s refusals again, so an empty mount point or a folder written into config.json by hand is never written to. Paths inside that folder are allowed even outside home, and nowhere else. `backup/move` packs what is plain, marks the new folder, points `backupDir` to it (config.json and its folder fsynced) and then moves every top-level entry of the copy but its marker, in one journal (`copyMove`) whose move entries name the copy folders they touch (scope `copy`, honoured only for moves and only for `<data dir>/history` or a marked folder). Where `backupDir` points is where the copy goes: Undo checks everything that can refuse it first (each folder's identity, that the setting still names the folder it moved to, that the old folder holds none of the names, that nothing works inside), then points the setting back and moves everything the copy holds back, also folders it gained since; only `backupDir` changes, so other settings edited since don't block it. A move or an Undo that fails is put back by moving back what it moved. While files move, `copy-move.json` in the data folder names the journal; the next backup or move, or an Undo of a move, finishes one that stopped by moving all of the copy into the folder the setting names (`ops::settle_copy`), and marks the journal applied or undone by that. A move it finishes is told in the Log with its Undo, whichever of the three finished it. It can't always finish at once: while the other drive is missing, full or in use, or a folder of the copy is in both places on a file system that can't rename without replacing (NFS, sshfs, 9p), it waits and says why, and the user puts that right outside Laci; a move that is put back stops the same way at such a folder and names both places. Nothing moves the copy while config.json is there but can't be read (`backup::settings`): the defaults would name another folder than the user's setting. Until then both folders are listed. Each move of a top-level entry is its own journal entry, in the way it went, with a token naming what a cross-device move sets aside and stages; the entry and the source's folder are fsynced before the copy is published on the other drive, and the copy and its folder before the source goes, so a stop at any step leaves either the source or a complete copy that the next run puts in place. Switching folders without moving anything drops `backup.json`, which described the copy left behind. A copy that can't be reached isn't moved unless `fresh` asks for a new copy in the new folder. Laci never makes a chosen folder or removes an emptied one. The scanner skips the chosen folder, and moves, archives and Trash refuse a project that holds it. `backup` and `backup/move` run outside the desktop's engine lock, like `delete/plan`, so a first run that packs gigabytes doesn't freeze the window; while one runs, other changes and an update's restart are refused at once instead of waiting for the change lock (`Engine::long_running`, `ops::LongRun`). `laci backup` runs the same backup from the command line, with the connectors from config.json and no scan.

Which chats the copy takes is `copy_choice.rs`. Without `backupOnly` in config.json it takes every file of every store, as before 3.2, and so does a `backupOnly` Settings couldn't have saved (not a list of full paths, or `outside` not true or false). `backupOnly` names the chosen folders (`paths`, as `~/…` in home, sorted, each once) and whether chats outside every project are copied (`outside`). A file's folder is the one its chat was started in. For a store that names its folders after the project (Claude Code), that is the store folder's name resolved as the scan resolves it (`resolve_encoded`); for a project that is gone, the first `cwd` its logs name, or else a known folder whose encoding is that name; a file at the top of the store is no project's. A Codex session goes by the first folder it names, as the scan files it. Another `cwd` store's log can hold the chats of several folders, as Antigravity's one `history.jsonl` does: it is copied when one of the folders it names in its field is chosen, and when it is longer than what is read of it (its first MiB, `agents::locations`). For a `sha256` store, the folder is the known one with that hash. The nearest known folder that holds it, among the scan's nodes and the chosen folders, decides; a folder in none of them is copied only with `outside`. A project that appears in a ticked group is a node of its own once scanned, so it isn't copied until it is ticked. A file whose folder can't be told, as Codex's index, is copied. The check runs only for files a run would write, after the length check, so an unchanged store costs no more than before. The window hands the copy its snapshot's nodes. `laci backup` reads them from the snapshot the window keeps in its cache (`snapshot-v2.json`, up to 128 MB); without one it knows only the chosen folders, which copies more, never less. Each run records the choice it copied by (`took` in `backup.json`). The scan counts as pending the chosen chats that changed since the last run or that it didn't take, as those of a project ticked since, so the hourly run takes them and the cleanup warning stays until it has; it reports `backup.only`: `paths` (full paths, as the nodes'), `outside`, `missing` (the chosen folders that aren't there now) and `notCopied`, the folders that hold chats that aren't copied. `backup/only` saves the choice with an Undo of its own (`copyChoice`, superseded by the next choice), which unticks what the change ticked and ticks again what it unticked, so what changed since, as a project Laci moved, stays. A move or a reconnect that moves a chosen folder writes a `chosen` journal entry with each chosen folder it moved and those it moved to that were chosen already; Undo moves each back unless it was unticked since and keeps those, on the settings as they are then, so settings changed since don't block it. Unticking a project removes nothing from the copy.

Deleting sessions (`session/delete`) is a journaled move into `orphans/sessions/<journal>/` of the data folder: the log, Claude Code's folder of subagent logs, and Laci's copies of both in the copy of AI chats: the log's would list the session again as backup-only, and nothing would ever list or remove the folder's. Undo moves them back. `storage/free` empties that quarantine for good and marks the journals that needed it, so the Log stops offering their Undo. Kept sessions live in `sessions.json` in the data folder, keyed by agent and session id.

The launch resolver (`launch.rs`) accepts a provider, optional session ID, project path, prompt, model, effort and terminal target. It builds each command from the provider's description: one argument per template element, and no shell. IPC resolves session membership from the snapshot and verifies an active connector. Internal PTYs receive executable/argv/cwd directly; external terminals use the same resolved arguments with quoted transport boundaries. Explicit model discovery is cached and does not start a conversation. Unsupported overrides fail without silently selecting another model or provider.

Desktop creation jobs run outside the snapshot mutex. They serialize filesystem creation through the existing process lock, bound output in memory, and fence mutations and stale snapshots from start through completion, failure or cancellation. Generator cancellation signals only its owned process group and reaps it before shutdown. Failed scaffolds stay on disk. Metadata, Git initialization and optional agent launch follow successful generation. Retrying a failed agent launch never repeats creation or remote operations.

Rust retains the submitted request and continuation in process memory until explicit acknowledgement. Startup restores the undismissed job after a WebView reload. Continuation claims are atomic and return cached results; explicit retries must match the failed attempt and always use the created project's path. A new creation cannot discard an undismissed job. No request or prompt is persisted for app-restart recovery.

Fresh configuration has no roots or connectors. Explicit empty roots survive save and Undo. Root identity records distinguish missing project paths from unavailable/replaced selected roots. Orphan proposals capture source fingerprints; applying one rechecks the proposal, confirmed project absence, protected paths, symlinks and active writers under the mutation lock. Quarantine remains the compatible default; Trash requires an explicit recovery choice and does not advertise Laci Undo.
